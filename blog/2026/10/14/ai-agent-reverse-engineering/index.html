AI 에이전트 역분석 도구, 기업은 어디까지 허용할 수 있을까

코딩 에이전트에 디컴파일러를 연결하는 역분석 도구가 퍼지고 있다. REA를 사례로 한국 저작권법 제101조의4와 제104조의2에 비춰 호환성 확보, 보안 점검, 기능 복제의 허용 범위를 판정하고, chardet 사례와 비교한 뒤 기업 내부 관리 기준을 제안한다.

AI 코딩 에이전트에 디컴파일러를 연결해 주는 도구가 빠르게 퍼지고 있습니다. 그중 하나인 REA(Reverse Engineer Anything)는 에이전트가 소스 코드 없이 앱을 살펴보고 그 기능의 동작을 설명한 뒤 “사용자의 프로젝트에 맞는 버전"까지 만들 수 있다고 소개합니다E3. 한국 저작권법은 프로그램코드역분석을 호환에 필요한 정보를 얻는 목적으로만 허용하므로A1, 같은 도구라도 호환성 확보, 보안 점검, 기능 복제 중 무엇에 사용하느냐에 따라 법적 판단이 달라집니다. 기업이 이런 도구를 허용하려면 분석 목적 확인, 분석 세션과 구현 세션의 분리, 분석 기록, 디컴파일러 라이선스 확인을 사내 기준에 넣어야 합니다.

1. AI로 상용 앱을 다시 만든다는 사례들

2026년 들어 상용 앱을 공개 소프트웨어로 다시 구현했다거나 그런 일을 대신해 준다는 프로젝트가 잇달아 주목을 받았습니다. 주장이 얼마나 사실로 확인되는지는 사례마다 다릅니다.

ArtCraft는 GitHub Organization storytold 아래에서 Craft 계열 앱을 공개하는 프로젝트이고F8, 그중 PhotoCraft는 Adobe Photoshop을 다시 구현했다고 내세웁니다. 2026-09-30에 만들어진 저장소의 README는 이 프로젝트를 “clean-room reimplementation of Adobe Photoshop"이라고 소개하고, 공개 명세와 관찰한 동작(“public specs and observed behaviour only”)만 근거로 삼았으며 독점 코드, 셰이더, 에셋은 사용하지 않았다고 밝힙니다(그림 1)F7. README 스스로 아직 “early alpha” 단계라 전문 작업용 대체품은 아니라고 적지만, 독일 매체 cloudmagazin은 10월 2일부터 7일 사이에 네 개 버전이 잇달아 나왔다고 보도했고F13, KDnuggets는 이를 “AI 소프트웨어 복제” 흐름의 사례로 다뤘습니다F14.

클린룸은 프로젝트가 스스로 붙인 설명입니다. 저장소는 개발에 어떤 AI 모델이나 역분석 도구를 사용했는지 밝히지 않고, 클린룸 주장을 제3자가 검증한 기록도 이번 조사에서는 찾지 못했습니다. 이런 결과물을 사내에 들여오거나 참고하려는 기업은 “클린룸으로 만들었다"는 문구만으로 원본 권리 문제가 해결되었다고 판단할 수 없습니다.

그림 1. PhotoCraft 저장소 README 상단. “clean-room reimplementation of Adobe Photoshop” 문구와 앱 실행 화면 (storytold/photocraftF7, 2026-10-14 캡처)

MALUS(malus.sh)는 “Clean Room as a Service"를 내건 사이트입니다(그림 2). 자사 AI가 어떤 오픈소스 프로젝트든 처음부터 다시 만들어 주므로, 결과물은 출처 표시나 카피레프트 의무 없이 사용할 수 있다고 홍보합니다F9. 오픈소스 라이선스 의무를 AI 재작성으로 지워 준다는 주장입니다.

다만 실제 서비스라기보다 문제 제기로 보입니다. 사이트의 CEO 서한은 Mike Nolan 명의인데, 그는 FOSDEM 2026에서 “Let’s end open source together with this one simple trick"이라는 발표를 공동으로 한 사람입니다F9·F10. 사이트에는 등록 관할을 “[JURISDICTION WITHHELD]“로 가린 표기처럼 풍자로 읽히는 요소가 여럿 있고, 확인일 현재 서비스가 일시 중단되었다는 문구가 표시됩니다. 실제로 주문을 받아 결과물을 납품했는지는 1차 기록으로 확인되지 않았습니다F9. 풍자라 하더라도 이런 사이트가 나왔다는 것은 AI 재작성으로 라이선스 의무를 피하는 일이 현실적인 걱정거리가 되었다는 뜻이고, 4장의 chardet 사례는 그 걱정이 실제 분쟁이 된 경우입니다.

그림 2. MALUS 사이트 첫 화면. 처리 건수 같은 숫자는 사이트가 표시한 값이며 확인되지 않음 (malus.shF9, 2026-10-14 캡처)

PhotoCraft와 MALUS에 대해 법원 판단이 나온 것은 이번 조사에서 확인되지 않았습니다. 그래도 “AI가 분석하고 AI가 다시 작성한다"는 작업 방식이 오픈소스 관리자의 검토 대상으로 들어온 것은 분명합니다.

이런 흐름과 함께 주목받은 분석 도구가 REA입니다. 재구현 결과물이나 대행 서비스가 아니라 에이전트에 연결해 사용하는 역분석 도구이고, 2장에서 보듯 같은 방식의 도구가 여럿 있으므로 아래 논의는 이 계열 도구 전체에 해당합니다. 저장소는 2026-04-14에 생성된 MIT 라이선스 프로젝트이며, 2026-10-14 GitHub API 기준 Star가 21만 개를 넘습니다E1. 생성 반년 만에 이만큼 모였다는 것은 관심이 크다는 뜻이지만, Star는 관심의 지표일 뿐 실제 도입 규모나 품질을 뜻하지는 않습니다.

2. 에이전트 역분석 도구가 바꾸는 개발 흐름

REA는 MCP(Model Context Protocol) 서버로 코딩 에이전트에 연결됩니다. README의 설명에 따르면 에이전트가 MCP로 REA를 호출해 대상을 점검하고, REA가 근거와 함께 결과를 돌려주며, 에이전트가 그 결과로 동작을 설명하거나 구현을 작성하고 테스트합니다. 네이티브 분석의 결과물은 어셈블리와 의사코드이고, 심층 분석에는 Hopper, Ghidra, IDA 중 하나를 엔진으로 사용합니다E3. 분석 자체는 로컬에서 실행되지만, 그 결과를 읽는 것은 에이전트이고 에이전트 뒤의 모델 제공자에게는 그 제공자의 데이터 정책(“its own data policy”)이 적용된다고 README가 직접 적고 있습니다E3. REA가 로컬 도구라도 분석 결과는 PC 밖으로 나갈 수 있다는 뜻입니다.

Hopper, Ghidra, IDA는 디스어셈블러이자 디컴파일러입니다. 배포된 실행 파일에는 CPU가 읽는 숫자 덩어리인 기계어만 들어 있습니다. 디스어셈블러는 이 기계어를 MOV, FMUL 같은 명령어 기호로 바꿔 보여 주고(어셈블리), 디컴파일러는 한 단계 더 나아가 C 언어와 비슷한 모양의 코드로 되돌립니다. 이렇게 되돌린 코드를 의사코드(슈도코드, pseudocode)라고 부릅니다. 원래 소스 코드가 아니라 기계어에서 추정해 만든 코드라서 변수 이름과 주석은 사라지고 FUN_00406400 같은 기계적인 이름이 붙으며, 빠지거나 틀린 부분도 생깁니다. 같은 함수가 어셈블리, 의사코드, 사람이 읽을 수 있게 복원한 C 코드로 각각 어떻게 보이는지는 아래 DX-Ball 사례(그림 5)에서 볼 수 있습니다.

Ghidra는 미국 국가안보국(National Security Agency, NSA)이 공개한 오픈소스 도구이고D8, IDA는 Hex-Rays의, Hopper는 Cryptic Apps의 상용 제품입니다D2·D7. REA가 직접 디컴파일하지는 않습니다. 이 도구 안에서 분석 스크립트를 실행해 결과를 받아 오고(그림 3), 에이전트는 그 결과를 읽습니다. JavaScript나 Electron 앱은 코드가 앱 패키지 안에 남아 있으므로 이런 엔진 없이 분석합니다E3.

디컴파일러를 AI 에이전트에 연결하는 방식은 REA만의 것이 아니고, REA 이전부터 있었습니다. 개인 개발자가 만든 Ghidra용 GhidraMCP와 IDA Pro용 ida-pro-mcp는 2025년 3월에 저장소가 생겼고E9·E10, 2026년에는 디컴파일러 회사가 직접 공식 MCP 서버를 내놓기 시작했습니다. 실제로는 어떻게 동작할까

REA 공식 사이트의 사례 하나를 따라가 보면 흐름이 구체적으로 보입니다. 1996년 Windows 게임 DX-Ball을 실행 파일로부터 유지보수 가능한 C 코드로 다시 만드는 프로젝트의 한 단계이고, 사례 페이지가 예로 든 지시는 “Use REA to find how DX-Ball calculates sound panning. Explain the calculation and show the code.“입니다E14.

  • 에이전트가 REA의 analyze_function으로 주소 0x406400의 함수를 분석했습니다. 디컴파일러가 내놓은 첫 의사코드는 입력이 없는 함수로 보여 계산식을 알 수 없었습니다.
  • 에이전트는 어셈블리 명령을 직접 읽어 숨은 입력을 찾았고, 이 함수를 부르는 쪽(0x411f40)을 분석해 그 입력이 벽돌의 화면 x좌표라는 것을 확인했습니다.
  • read_bytes로 실행 파일 안의 상수 1.5625와 500.0을 읽었습니다.
  • 이를 바탕으로 C 함수 dxball_screen_pan을 작성하고 원본과 3,205가지 경우의 결과를 비교했습니다. 당시 컴파일러(VC4.0)로 다시 컴파일하면 원본 함수와 같은 기계어 63바이트가 나온다고 사례 페이지는 밝힙니다.

그림 5. DX-Ball의 같은 함수를 세 단계로 본 모습. 디컴파일러의 의사코드에서 빠진 계산을 에이전트가 어셈블리와 상수로 보완함 (REA 사례 페이지E14의 코드를 옮겨 작성, 2026-10-14)

같은 사이트의 Notion 사례는 상용 앱의 기능을 추적한 경우입니다. 에이전트는 Notion 데스크톱 앱에 패키지된 JavaScript를 분석해, 복사한 텍스트와 HTML이 시스템 클립보드에 쓰이기까지의 호출 경로를 단계별 코드와 함께 보여 줬습니다E15. 이 사례 페이지는 분석 권한을 언급하지 않습니다.

클린룸 관행과 부딪히는 지점

분석과 구현이 한 세션에서 이어지는 구조는 기존 클린룸 관행과 부딪힙니다. 클린룸 설계는 원본을 분석하는 팀과 구현하는 팀을 나누고, 구현팀은 원본 대신 기능 명세서만 보고 작업하는 방식입니다F18. 반면 에이전트 세션에서는 디컴파일 결과를 받은 바로 그 컨텍스트에서 구현 코드가 작성됩니다. 분석과 구현 사이에 사람이 검토한 명세서라는 차단 단계가 없으므로, 나중에 “원본 표현을 보지 않고 만들었다"고 설명할 근거가 남지 않습니다.

3. 한국 저작권법으로 본 목적별 판정

법이 허용하는 역분석의 범위

현행 저작권법(법률 제21336호, 2026-08-11 시행)은 역분석의 정의에 목적을 넣어 두었습니다A1.

제2조 제34호 “프로그램코드역분석"은 독립적으로 창작된 컴퓨터프로그램저작물과 다른 컴퓨터프로그램과의 호환에 필요한 정보를 얻기 위하여 컴퓨터프로그램저작물코드를 복제 또는 변환하는 것을 말한다.

허용 요건과 정보 이용 제한은 제101조의4에 있습니다A1.

제101조의4(프로그램코드역분석)

① 정당한 권한에 의하여 프로그램을 이용하는 자 또는 그의 허락을 받은 자는 호환에 필요한 정보를 쉽게 얻을 수 없고 그 획득이 불가피한 경우에는 해당 프로그램의 호환에 필요한 부분에 한정하여 프로그램의 저작재산권자의 허락을 받지 아니하고 프로그램코드역분석을 할 수 있다.

② 제1항에 따른 프로그램코드역분석을 통하여 얻은 정보는 다음 각 호의 어느 하나에 해당하는 경우에는 이를 이용할 수 없다.

제1호 호환 목적 외의 다른 목적을 위하여 이용하거나 제3자에게 제공하는 경우

제2호 프로그램코드역분석의 대상이 되는 프로그램과 표현이 실질적으로 유사한 프로그램을 개발ㆍ제작ㆍ판매하거나 그 밖에 프로그램의 저작권을 침해하는 행위에 이용하는 경우

제1항의 요건은 네 가지이고 모두 충족해야 합니다. 정당한 권한을 가진 이용자일 것, 호환 정보를 쉽게 얻을 수 없을 것, 획득이 불가피할 것, 호환에 필요한 부분에 한정할 것입니다. 기능 조사에 관해서는 제101조의3 제1항 제6호가 따로 있습니다. 같은 항은 “그 목적을 위하여 필요한 범위에서 공표된 프로그램을 복제 또는 배포할 수 있다"고 하면서, 저작재산권자의 이익을 부당하게 해치는 경우는 제외합니다A1.

제101조의3 제1항 제6호 프로그램의 기초를 이루는 아이디어 및 원리를 확인하기 위하여 프로그램의 기능을 조사ㆍ연구ㆍ시험할 목적으로 복제하는 경우(정당한 권한에 따라 프로그램을 이용하는 자가 해당 프로그램을 이용 중인 경우로 한정한다)

이 조항은 역분석 조항과 달리 호환 목적이 아니어도 됩니다. 대신 허용되는 것은 아이디어와 원리를 확인하기 위한 복제이고, 그 프로그램을 정당하게 이용하고 있어야 합니다. 동작 원리를 이해하는 데까지는 이 조항을 근거로 삼을 수 있지만, 그 결과를 제품 코드로 옮기는 단계는 이 조항이 다루지 않습니다.

기술적 보호조치가 걸려 있으면 제104조의2가 함께 적용됩니다. 기술적 보호조치는 암호화나 라이선스 검사처럼 무단 이용을 막으려고 저작물에 걸어 둔 장치를 말합니다. 이런 장치를 풀어야 분석할 수 있는 프로그램이라면, 역분석이 허용되는 경우에도 이 조항을 따로 따져야 합니다. 제1항 본문은 “누구든지 정당한 권한 없이 고의 또는 과실로 제2조제28호가목의 기술적 보호조치를 제거ㆍ변경하거나 우회하는 등의 방법으로 무력화하여서는 아니 된다"이고, 역분석과 관련된 예외는 다음 세 호입니다A1.

제104조의2 제1항 제1호 암호 분야의 연구에 종사하는 자가 저작물등의 복제물을 정당하게 취득하여 저작물등에 적용된 암호 기술의 결함이나 취약점을 연구하기 위하여 필요한 범위에서 행하는 경우. 다만, 권리자로부터 연구에 필요한 이용을 허락받기 위하여 상당한 노력을 하였으나 허락을 받지 못한 경우로 한정한다.

제104조의2 제1항 제6호 정당한 권한을 가지고 프로그램을 사용하는 자가 다른 프로그램과의 호환을 위하여 필요한 범위에서 프로그램코드역분석을 하는 경우

제104조의2 제1항 제7호 정당한 권한을 가진 자가 오로지 컴퓨터 또는 정보통신망의 보안성을 검사ㆍ조사 또는 보정하기 위하여 필요한 경우

EU 컴퓨터 프로그램 지침 2009/24/EC 제6조는 디컴파일 허용 요건으로 권한 있는 이용자, 상호운용 정보를 미리 쉽게 얻을 수 없을 것, 필요한 부분에 한정할 것을 두고, 얻은 정보를 “substantially similar in its expression” 프로그램 개발에 사용하지 못하게 합니다A3. 조문을 대조해 보면 한국 제101조의4와 구조가 거의 같습니다. 차이는 계약입니다. 제8조 둘째 문단은 “Any contractual provisions contrary to Article 6 or to the exceptions provided for in Article 5(2) and (3) shall be null and void.“라고 정합니다A3. EULA에 역분석 금지 조항을 넣어도 EU에서는 법이 허용한 범위의 디컴파일까지 막을 수 없다는 뜻입니다. 한국 저작권법 제101조의3과 제101조의4에는 이와 같은 문구가 없으며A1, 다른 법리로 같은 효과를 인정한 국내 판례도 확인하지 못했습니다.

미국은 법 조항보다 판례로 기준을 정했습니다. Sega Enterprises Ltd. v. Accolade, Inc.(9th Cir. 1992)는 Sega 게임기와 호환되는 게임을 만들려고 Sega의 프로그램을 디스어셈블한 행위를, 호환에 필요한 정보를 얻을 방법이 그것뿐이었고 정당한 이유도 있었으므로 공정이용으로 보았습니다B1. Sony Computer Entertainment, Inc. v. Connectix Corp.(9th Cir. 2000)도 PlayStation 호환 에뮬레이터를 개발하는 과정에서 생긴 복제를 공정이용으로 인정했습니다B2. 두 판결이 허용한 것은 분석 과정의 복제이고, 그렇게 만든 최종 제품이 원본을 침해하는지는 따로 따집니다. 한국 제101조의4 제2항 제2호와 같은 구분입니다. 법령으로는 17 U.S.C. §1201(f)가 상호운용을 위한 보호조치 우회를, §1201(j)가 소유자나 운영자의 승인을 받은 보안 검사를 예외로 둡니다A4.

계약 쪽에는 반대 방향의 판결이 있습니다. Bowers v. Baystate Technologies, Inc.(Fed. Cir. 2003)에서 법원 다수의견은 역분석을 금지한 슈링크랩(shrink-wrap) 라이선스, 곧 포장을 뜯으면 동의한 것으로 보는 약관을 유효하다고 보고 계약 위반 책임을 인정했습니다B3. 저작권법이 허용하는 역분석이라도 계약으로 금지했다면 계약 위반이 될 수 있다는 뜻입니다. 반대 의견이 있었고 미국 전체에서 확립된 원칙도 아니지만, 역분석 도구를 사용하기 전에 대상 소프트웨어의 EULA부터 읽어야 하는 이유를 보여 줍니다. 한국에서 같은 문제를 어떻게 판단할지는 아직 정해지지 않았습니다.

영업비밀과 특허는 어떻게 볼까

영업비밀 위험은 흔히 말하는 것보다 좁습니다. 부정경쟁방지 및 영업비밀보호에 관한 법률(법률 제21065호, 2026-05-28 시행)이 침해로 보는 취득은 “절취(竊取), 기망(欺罔), 협박, 그 밖의 부정한 수단"에 의한 것이고(제2조 제3호 가목), 같은 호에 역설계나 역분석이라는 단어는 없습니다A2. 시중에서 정상적으로 산 제품을 분석하는 데에는 훔치거나 속이는 일이 끼어들 여지가 적으므로, 그것만으로 침해가 되기는 어렵다고 해석할 수 있습니다. 판례가 아니라 조문에 근거한 해석입니다. 미국은 이를 법에 적어 두었습니다. 영업비밀보호법(Defend Trade Secrets Act of 2016, DTSA)으로 개정된 18 U.S.C. §1839(6)(B)는 “improper means"에 “reverse engineering, independent derivation, or any other lawful means of acquisition"이 포함되지 않는다고 명시합니다A5. 국내에는 이런 명문 규정이 없고, 역설계를 정당한 취득으로 인정했거나 침해로 본 판례도 이번 조사에서는 확인하지 못했습니다.

예외는 비밀유지 약정을 맺고 받은 바이너리입니다. 이 경우에는 같은 호 라목의 비밀유지 의무 위반 문제가 따로 생기므로 구분해서 다뤄야 합니다A2.

특허는 역분석의 적법성과 무관하게 따로 봐야 합니다. 특허법 제94조 제1항은 “특허권자는 업으로서 특허발명을 실시할 권리를 독점한다"고 정하고A8, 이 조문에는 독립 개발 여부가 요건으로 들어 있지 않습니다. 저작권법상 문제없이 분석하고 표현을 새로 작성했더라도, 구현한 기능이 특허 청구항에 해당하면 침해가 성립할 수 있습니다.

AI 재작성이 실제 분쟁이 된 사례는 오픈소스 쪽에서 먼저 나왔습니다. chardet은 텍스트의 문자 인코딩을 알아내는 Python 라이브러리입니다. 관리자 Dan Blanchard는 2026-03-04(UTC) chardet 7.0.0을 내면서 릴리스 노트에 “Ground-up, MIT-licensed rewrite of chardet. LGPL은 라이브러리를 배포할 때 소스 코드를 함께 제공하도록 요구하는 등 조건이 붙지만 MIT는 저작권 고지만 남기면 되므로, 라이선스가 바뀌면 사용자의 의무가 크게 줄어듭니다. 같은 날 원저작자 Mark Pilgrim은 이슈 #327 “No right to relicense this project"를 열어, 원본 코드에 노출된 상태에서 다시 작성한 것은 클린룸이 아니므로 라이선스 변경은 LGPL 위반이라고 주장했습니다F2.

이 논쟁에서 클린룸 주장은 처음부터 약했습니다. Blanchard는 같은 이슈의 pinned comment에서 자신이 원본 코드에 광범위하게 노출되어 전통적 클린룸의 분리를 주장할 수 없다고 인정했고, 다른 참여자는 원본 파일을 가져와 기준으로 삼으라는 지시가 담긴 에이전트 작업 계획 문서의 커밋을 링크했습니다. 그 참여자도 실제 실행 여부는 더 조사하지 않았다고 단서를 달았습니다F2. Blanchard는 같은 pinned comment에서 코드 표절 검사 도구 JPlag로 측정한 구조 유사도(직전 릴리스 대비 최대 1.29%)를 독립성의 근거로 제시했으나F2, 측정에 사용한 원 리포트는 공개되지 않았습니다.

5. 에이전트가 만든 구현물의 저작권

에이전트가 만든 코드는 회사의 자산으로서도 약할 수 있습니다. Thaler v. Perlmutter는 Stephen Thaler가 자신의 AI 시스템이 스스로 만든 그림을 저작권 등록하려다 거절당해 다툰 사건입니다. 미국 컬럼비아 특별구 연방항소법원은 2025-03-18 저작권법이 인간 저작자를 요구한다며 등록 거절을 유지했고B4, 연방대법원은 2026-03-02 상고 신청을 기각했습니다(No. 25-449)B5. 대법원이 사건을 심리하지 않기로 한 것이라 대법원 스스로 판단을 내린 것은 아니지만, 항소법원 판결은 그대로 남았습니다. 미국 저작권청의 Part 2 보고서(2025-01)도 순수하게 AI가 생성했거나 표현 요소에 대한 인간의 통제가 불충분한 자료에는 저작권이 미치지 않고, 현재 기술에서 프롬프트만으로는 통제가 충분하지 않다고 결론지었습니다C1.

한국도 방향이 같습니다. 문화체육관광부와 한국저작권위원회의 「생성형 인공지능 활용 저작물의 저작권 등록 안내서」(2025-06)는 인간의 창작적 기여가 없는 생성형 AI 산출물은 등록할 수 없고, 프롬프트 입력은 일반적으로 “아이디어 제공 또는 지시 정도"라 창작적 기여로 인정될 가능성이 낮다고 설명합니다. 산출물을 수정·증감한 부분이나 선택·배열에 창작성이 있으면 그 부분은 인정됩니다. 안내서는 컴퓨터프로그램저작물도 같은 기준으로 등록할 수 있다고 적지만 코드 사례는 싣지 않았습니다C3.

기업에 주는 시사점은 두 가지입니다. 에이전트가 역분석 결과를 보고 거의 그대로 작성한 구현물은 원본 권리자에게는 침해 시비를 받을 수 있으면서도, 정작 회사가 제3자의 복제를 막을 권리는 약할 수 있습니다. 또 “AI가 새로 작성한 코드이니 우리 소유"라는 설명은 성립하기 어렵습니다. Plagiarism Today가 MALUS의 “legally distinct code that you own outright"라는 문구를 이 이유로 반박한 것도 같은 맥락입니다F11.

허용 목적을 목록으로 정해 둡니다

허용 목적은 자사 소유 또는 계약상 점검 권한이 있는 소프트웨어의 디버깅·감사, 보안 점검과 취약점 분석, 공개 문서로 해결되지 않는 호환성 확보 정도로 좁히는 편이 안전합니다. 타사 제품의 기능을 재현하기 위한 분석은 원칙적으로 허용 목록에 넣지 않고, 꼭 필요하면 법무 사전 승인 대상으로 둡니다. REA DISCLAIMER의 허용 목적 목록도 출발점으로 참고할 만합니다E4. 다만 도구 문서가 허용한다고 해서 법적 허용이 생기지는 않습니다.

클린룸을 에이전트 세션 단위로 나눕니다

분석과 구현을 서로 다른 에이전트 세션으로 분리합니다. 분석 세션은 기능 명세(입출력, 데이터 형식, 프로토콜 동작)만 산출하고, 사람이 그 명세에 의사코드나 원본 식별자가 섞이지 않았는지 검토한 뒤 구현 세션에 넘깁니다. 구현 세션에는 역분석 MCP 서버를 연결하지 않고, 디컴파일 결과 파일이 있는 경로에 접근하지 못하게 설정합니다. chardet 사례에서 작업 계획 문서에 원본 파일을 참조하라는 지시가 남아 있던 것이 그대로 반론의 근거가 되었듯이F2, 세션 분리는 설정과 로그로 증명할 수 있어야 의미가 있습니다.

MCP 서버 도입 승인 절차에 넣습니다

역분석 MCP 서버도 다른 MCP 서버와 같은 도입 승인 절차에 넣습니다. MCP 명세는 도구 호출을 임의 코드 실행으로 보고 조심해서 다루라고 하며, Claude Code 같은 에이전트 앱(명세에서는 호스트라고 부릅니다)이 도구를 실행하기 전에 사용자의 명시적 동의를 받도록 정합니다. 그러나 명세 스스로 밝히듯 프로토콜이 이를 강제하지는 못하므로, 실제 통제는 에이전트 앱 설정과 회사 정책에 달려 있습니다E8. 역분석 MCP 서버는 분석 대상 프로그램을 실행하거나 연결된 기기를 조작하기도 합니다. REA DISCLAIMER도 “Local operation does not establish authorization”, 곧 내 PC에서 실행한다고 분석 권한이 생기지는 않는다고 적습니다E4.

그래서 일반 MCP 서버 심사 항목(배포 출처, 권한 범위, 데이터 반출 경로)에 세 가지를 더하는 것이 좋습니다. 무엇을 분석하는 데 사용할 것인지 목적을 확인하고, 연결될 디컴파일러의 에디션과 라이선스를 확인하고, 디컴파일 결과가 외부 모델로 전송되는지 확인합니다. REA처럼 릴리스가 잦은 도구는E3 버전을 고정하고 바꿀 때마다 다시 확인하며, 그 서버로 만든 코드에는 커밋 단위로 AI 사용 사실을 남깁니다.

7. 맺음말

에이전트 역분석 도구는 디컴파일러 회사가 공식 기능으로 내놓을 만큼 이미 퍼졌습니다. 개발자가 MCP 서버 하나만 연결하면 사용할 수 있는 환경에서는 도입 자체를 금지하기보다, 어디까지 허용할지를 정해 두는 편이 현실적입니다.

허용 범위를 정하는 기준은 분석이라는 행위보다 목적과 결과물입니다. 호환성 확보와 보안 점검은 저작권법에 근거 조항이 있지만, 타사 기능을 복제하려는 분석은 근거 조항이 없습니다. 결과물이 원본과 표현이 실질적으로 유사하면 침해가 되고, DX-Ball 사례처럼 원본과 같은 기계어가 나오도록 맞춘 코드는 그 판단에서 가장 불리한 쪽에 놓입니다. 에이전트가 분석과 구현을 한 세션에서 처리하면 유사하지 않다는 근거를 남기기도 어렵습니다.

기업이 먼저 할 일은 세 가지입니다. 허용 목적을 목록으로 정하고, 사내에서 사용하는 디컴파일러의 에디션과 약관을 확인하고(IDA Free처럼 상업 이용이 금지된 에디션이 업무에 연결되어 있지 않은지), 분석 세션과 구현 세션을 나눠 그 사실을 기록으로 남기는 것입니다. EULA의 역분석 금지 조항이 국내에서 효력이 있는지, 제101조의3 제1항 제6호가 디컴파일까지 허용하는지는 아직 판례로 정해지지 않았으므로, 이 두 쟁점은 사안마다 법무와 함께 판단하고 관련 판례가 나오면 기준을 다시 확인해야 합니다.
